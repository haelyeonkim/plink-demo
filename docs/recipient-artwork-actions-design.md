# 수신자 액션 기능 설계안

**작품별로 수신자가 의사를 표시하고, 관리자가 홀딩·판매를 확정하는 구조**를 추천합니다. 핵심은 ‘수신자의 의사’와 ‘작품의 판매 상태’를 분리하는 것입니다.

현재 코드에는 수신자별 링크, 작품의 홀딩·판매 상태, 활동 로그가 있어 이를 확장할 수 있습니다. 아래는 구현 전 설계 제안입니다.

### 1. 수신자 액션과 단계

액션 단위는 **수신자 × 작품**입니다. 하나의 링크로 여러 작품을 전달해도 작품마다 따로 선택합니다.

| 단계 | 수신자 액션 | 처리 방식 | 작품 상태 영향 |
|---|---|---|---|
| 관심 있음 | 관심 표시 | 즉시 반영 | 없음 |
| 홀딩 요청 | 홀딩 신청 | 관리자 승인 대기 | 없음 |
| 홀딩 확정 | 관리자가 승인 | 홀딩 종료 시각 안내 | 홀딩 |
| 구매 의사 | 구매 상담 요청 | 관리자에게 확인 요청 | 기존 상태 유지 |
| 판매 완료 | 관리자가 확정 | 거래 완료로 표시 | 판매 완료 |

- 관심 표시를 거치지 않고 홀딩 요청이나 구매 의사를 바로 보낼 수 있습니다.
- **구매 의사 표시는 결제나 판매 확정으로 처리하지 않습니다.**
- 홀딩 중에도 구매 의사를 표시할 수 있으므로, 구매 의사와 홀딩 정보는 별도로 유지합니다.
- 다른 수신자에게 홀딩된 작품은 관심 표시까지 허용하고, 추가 홀딩 요청은 막는 것을 1차 범위로 추천합니다.

### 2. 취소 범위 추천

**판매 확정 전에는 본인의 의사를 직접 철회할 수 있게 하고, 판매 확정 후에는 관리자에게 취소를 요청**하도록 합니다.

| 현재 상태 | 수신자 취소 | 취소 결과 |
|---|---|---|
| 관심 있음 | 즉시 가능 | 관심 해제 |
| 홀딩 승인 대기 | 즉시 가능 | 요청 철회 |
| 홀딩 확정 | 즉시 가능 | 본인의 홀딩 해제, 관리자에게 표시 |
| 구매 의사 전달 | 판매 확정 전 가능 | 구매 의사 철회 |
| 판매 완료 | 직접 변경 불가 | 관리자에게 취소 요청 |

세부 정책은 다음처럼 명확히 두는 것이 좋습니다.

- **홀딩 취소와 구매 의사 철회는 별개입니다.** 구매 의사를 철회할 때 홀딩도 해제할지 명시적으로 선택합니다.
- 홀딩 요청 시 기존 관심 여부를 보존합니다. 홀딩 취소가 자동으로 관심 해제까지 이어지지는 않습니다.
- 홀딩은 승인 시 종료 시각을 지정하고, 기한이 지나면 자동 해제합니다.
- 취소해도 과거 기록은 삭제하지 않습니다. 재신청은 새 이력으로 남깁니다.
- 링크가 만료되거나 회수되어도 기존 요청이 자동 취소되지는 않습니다. 수신 화면에는 담당자 연락 경로를 안내하고, 관리자가 처리할 수 있게 합니다.

### 3. 수신자 화면

작품 카드 또는 상세 화면에 현재 상태와 가능한 액션을 표시합니다.

예시:

> **홀딩 확정 · 11월 12일 18:00까지**  
> [구매 의사 전달] [홀딩 취소]  
> 구매 의사를 전달하면 담당자가 거래 절차를 안내합니다.

요청 후에는 버튼만 바꾸지 말고 **접수 시각·처리 상태·취소 가능 여부**를 함께 보여줍니다. 다른 수신자의 이름이나 요청 내역은 노출하지 않습니다.

### 4. 관리자 화면과 로그

관리자는 두 관점에서 확인할 수 있어야 합니다.

- **요청 목록:** 수신자, 작품, 요청 종류, 현재 상태, 요청 시각, 홀딩 기한. 승인 대기·구매 의사·취소 요청으로 필터링.
- **작품/수신자 상세 이력:** 관심 표시부터 승인·철회·만료·판매까지 시간순으로 표시.

이력에는 다음을 저장합니다.

| 항목 | 내용 |
|---|---|
| 대상 | 작품, 수신자, 전달 링크 |
| 행위자 | 수신자 / 관리자 / 시스템 |
| 액션 | 관심 표시·해제, 홀딩 요청·승인·거절·취소·만료, 구매 의사·철회, 판매 확정 |
| 변경 내용 | 이전 상태 → 이후 상태 |
| 부가 정보 | 처리 시각, 사유, 홀딩 기한, 요청 식별자 |

예: `김○○ · 작품 A · 홀딩 취소 · 홀딩 확정 → 해제 · 14:32`

**현재 활동 로그는 비동기 방식이므로, 이 기능의 유일한 거래 이력으로 사용하기에는 부족합니다.** 상태 변경과 전용 이력 저장을 같은 DB 트랜잭션으로 처리하고, 기존 활동 로그에도 함께 남기는 구성을 추천합니다.

### 5. 구현 시 지켜야 할 규칙

- 액션은 기존 수신자 인증을 통과한 세션에서만 허용합니다. 링크 주소를 알고 있다는 이유만으로 처리하지 않습니다.
- 서버에서 해당 링크에 포함된 작품인지, 본인의 요청인지, 현재 가능한 변경인지 검사합니다.
- **같은 작품에 활성 홀딩은 하나만 허용**하고, 동시 승인도 DB에서 차단합니다.
- 중복 클릭이나 재전송으로 요청·이력이 중복 생성되지 않게 합니다.
- 관리자 승인과 수신자 취소가 동시에 발생하면 먼저 확정된 상태를 기준으로 재검증합니다.
- 기존 관리자의 직접 홀딩·판매 변경도 같은 처리 규칙을 거치게 하여 수신자 요청과 어긋나지 않도록 합니다.
- 작품 라이브러리에 연결되지 않은 전달용 스냅샷은 1차 버전에서 액션 대상에서 제외합니다.

### 6. 권장 1차 범위

**관심 표시/해제 → 홀딩 요청/승인/거절/취소/만료 → 구매 의사/철회 → 관리자 판매 확정**, 그리고 관리자 요청 목록과 변경 이력까지 포함합니다.

자동 홀딩 승인, 대기 순번, 결제·환불 연동, 단계별 이메일 알림은 후속 범위로 두는 것이 좋습니다. 우선 **관리자 승인형 홀딩과 판매 확정 전 직접 철회**를 기본 정책으로 잡으면, 수신자 편의와 작품 배정 관리를 함께 충족할 수 있습니다.
