# 관리자 작품 요청: 설계 및 구현

보낸 링크에서 발생한 작품 반응을 한 화면에 모으고, 접수순으로 검토하며 수신자별 상태 변경 이력을 연결한다. 기존 수신자 액션과 관리자 승인·판매 처리를 확장한 구현이다. 이 문서는 Draft PR의 검토 기준이며 운영 반영 완료를 뜻하지 않는다.

## 1. 화면 구성

기본 경로는 `/links/requests`이고 기존 계정 소유자용 `/admin/artworks/requests`에서도 같은 컴포넌트를 사용한다. 링크 도구 상단 메뉴, 링크 목록의 `작품 요청`, 개별 링크의 `작품 요청` 버튼으로 진입한다. 개별 링크에서 진입하면 `linkId` 필터가 적용된다.

| 영역 | 구성과 동작 |
| --- | --- |
| 상태 요약 | 전체 반응, 관심, 홀딩 요청, 홀딩 확정, 구매의사, 현재 반응 없음, 판매 완료, 판매 취소 요청의 건수. 클릭하면 해당 상태로 필터링 |
| 검색·필터 | 작품·수신자·링크 제목 검색, 요청 상태, 처리 상태, 전달 링크, 작품, 발신 계정, 접수 기간(UTC), 구매의사 철회 이력 여부 |
| 정렬 | 기본 접수 빠른 순. 선택 시 수신자의 구매의사 철회 횟수가 많은 순 |
| 요청 목록 | 작품명, 수신자 이메일, 전달 링크, 현재 상태, 철회 횟수, 접수 시각, 최초 반응 시각, 처리 상태, 담당자, 홀딩 기한. 페이지당 30건 |
| 행별 이동 | 이 작품 요청 모아보기, 이 링크 반응, 전달 링크 상세 이동 |
| 상태 처리 | 현재 상태에 따라 홀딩 승인·거절·해제, 판매 확정, 판매 취소 승인·거절 버튼 표시 |
| 담당 / 메모 | 미확인·확인·상담 중·처리 완료, 담당자, 내부 메모를 하단 패널에서 저장 |
| 이력 | 접근 가능한 링크에 걸친 동일 수신자의 상태 변경 이력과, 선택한 요청의 관리자 처리 기록. 각 50건 단위 페이지 이동 |

요약 카드는 모바일에서 2열로 표시한다. 로딩·빈 목록·오류·새로고침을 제공하고 처리 및 이력 패널을 열면 제목으로 포커스를 이동한다. 검색어와 페이지는 화면 상태이며, 나머지 필터는 URL 쿼리에 반영한다.

## 2. 요청 단위와 접수순

- 목록 한 행은 링크에 발급된 수신자 × 작품이다. 같은 사람이 다른 링크에서 반응하면 별도 요청이며 이력에서 연결한다.
- 요약 집계용 대표 상태는 `판매 취소 요청 → 판매 완료 → 구매의사 → 홀딩 확정 → 홀딩 요청 → 관심 → 현재 반응 없음` 순서로 하나만 선택한다. 원래 관심·홀딩·구매의사 상태 자체는 별도로 유지한다.
- 전체 반응은 관심·홀딩 요청·홀딩 확정·구매의사의 합이다. 판매 완료·판매 취소 요청·현재 반응 없음은 제외한다. 비율의 분모는 전체 반응이다.
- 요약은 검색·링크·작품·처리 상태·기간 등 필터를 반영하되, 요청 상태 탭으로 좁히기 전의 건수를 표시한다.
- 기본 정렬은 현재 유효한 요청의 접수 시각 오름차순, 동률이면 요청 ID 오름차순이다. 구매의사는 `purchase_at`, 홀딩은 `hold_requested_at`, 관심은 `interest_at`을 사용한다. 판매·취소 요청 등은 `requested_at`을 사용하고 없는 값은 최종 변경 시각으로 보완한다.
- 최초 반응 시각 `first_requested_at`은 별도 보존한다. 관리자 처리나 같은 선택의 반복은 순서를 바꾸지 않는다. 구매의사 철회 후 다시 전달하면 새 구매의사 접수 시각으로 정렬한다.
- 접수순은 확인 순서이며 홀딩·구매 우선권을 자동 부여하지 않는다. 기간 필터도 이 접수 시각을 기준으로 UTC 날짜의 시작 이상, 종료일 다음 날 시작 미만을 조회한다.

## 3. 관리자 처리 흐름

1. 요약과 필터에서 검토할 요청을 선택한다.
2. 수신자 이력에서 이전 상태·이후 상태, 행위자, 발생 시각, 작품·링크, 사유와 홀딩 기한을 확인한다.
3. 담당자·내부 메모·처리 상태를 저장하거나 기존 홀딩·판매 액션을 실행한다.
4. 새 수신자 반응이 들어오면 처리 상태를 `UNREAD`로 되돌린다. 담당자와 메모는 유지한다.

홀딩 승인에는 종료 시각이 필요하다. 홀딩 거절과 판매 취소 승인·거절에는 사유가 필요하다. 구매의사는 결제 또는 판매 확정이 아니며 판매는 관리자가 확정한다. 취소 승인 시 실제 결제 환불은 별도 처리한다.

담당자·메모 변경은 이전/이후 값과 처리자를 전용 이력에 저장한다. 저장 시 `version`을 검사하고 변경 충돌은 HTTP 409로 반환한다. 수신자 변경과 같은 작품 잠금 순서를 사용한다.

## 4. 수신자별 이력과 권한

- 동일 `recipient_id`, 또는 동일한 검증된 패스키 사용자 `holder_id`로 이력을 연결한다. 같은 이름·이메일만으로 다른 수신자를 합치지 않는다.
- 구매의사 표시·철회 횟수는 수신자가 수행한 `PURCHASE`·`WITHDRAW` 이벤트만 센다. 관리자나 시스템의 종료는 철회 횟수에서 제외한다.
- 계정 소유자(`AdminPrincipal.owner`)는 전체 요청을 볼 수 있다. 일반 링크 관리자는 요청에 저장된 `owner_sub`가 본인인 요청만 조회·처리한다. 수신자 이력·집계·필터 선택지에도 같은 범위를 적용한다.
- 접근 범위 밖의 요청 상세·변경은 404로 처리한다. 내부 메모·담당자·관리자 처리 이력은 수신자 응답에 포함하지 않는다.
- 링크·초대 삭제 후에도 권한과 수신자 식별을 유지하기 위해 소유자·검증된 수신자·링크 제목을 요청에 보존한다. 과거 발신자를 복구할 수 없는 기록은 계정 소유자에게만 표시한다.

## 5. API와 코드 구성

기본 API는 `/api/links/artwork-requests`이며 계정 소유자 전용 `/api/admin/artworks/requests` 경로도 지원한다. 조회 응답에는 `Cache-Control: no-store`를 적용한다.

| 메서드·경로 | 역할 |
| --- | --- |
| `GET /` | 요청 목록, 총 건수, 상태 집계, 링크·작품·발신 계정 선택지 |
| `POST /{id}` | 기존 홀딩·판매 상태 변경 |
| `GET /{id}/history` | 기존 단일 요청 변경 이력 |
| `GET /{id}/recipient-history?page=0` | 수신자 통합 이력, 구매의사·철회 횟수 |
| `POST /{id}/work` | version, processingState, assignee, internalNote 저장 |
| `GET /{id}/work-history?page=0` | 해당 요청의 관리자 처리 이력 |

- `ArtworkRequests.tsx`: 요청 화면, 처리 패널, 수신자·관리자 이력 표시.
- `ArtworkRequestController`: 기존·신규 경로 연결과 요청별 접근 검사.
- `ArtworkRequestInbox`: 권한 범위, 검색·집계·정렬, 수신자 연결, 내부 처리 기록.
- `ArtworkRequestService`: 기존 상태 전이 유지, 접수 시각 기록, 반복 선택 무변경 처리, 새 반응 시 미확인 전환.
- `SecurityConfig`: 링크 관리자·계정 관리자용 API 접근 규칙.

## 6. DB 변경과 배포 영향

`V59__artwork_request_inbox.sql`에서 다음을 추가한다.

- 요청 스냅샷: `owner_sub`, `holder_id`, `link_title`.
- 접수 시각: `first_requested_at`, `requested_at`, `interest_at`, `hold_requested_at`, `purchase_at`.
- 내부 처리: `processing_state`, `assignee`, `internal_note`.
- 관리자 처리 이력 테이블: `artwork_request_work_event`.
- 소유자·접수 시각, 수신자 식별자, 처리 이력 조회 인덱스.

기존 요청은 링크·수신자 테이블과 상태 변경 이벤트에서 보완한다. 새 환경변수는 없다. 실제 운영 DB에는 이 작업에서 마이그레이션을 실행하지 않는다. 배포 시 기존 행 보완 작업이 수행되므로 운영 데이터량에 따른 소요 시간은 별도로 확인해야 한다.

## 7. 검증 범위와 검토 사항

추가 테스트는 소유권별 목록·요약·이력·변경 제한, 비공개 메모, 버전 충돌, 새 반응의 미확인 전환, 중복 집계 방지, 접수순·재요청 순서, UTC 기간 필터, 검증된 수신자 연결, 기존 DB 보완을 다룬다. 브라우저 스크립트는 격리된 H2와 합성 데이터로 수신자 인증부터 요청·판매·취소, 이력·필터·내부 메모와 모바일 레이아웃까지 확인한다.

검증 실행 결과는 Draft PR 본문에 기록한다. 브라우저 스크립트는 빌드된 JAR과 13002 포트의 Vite(백엔드 18082 프록시)가 필요하다.

Draft 검토 시 확인할 사항:

- 최초 반응순 대신 현재 유효한 요청의 접수순을 쓰는 정책과 철회 후 재접수 동작.
- 수신자 통합 이력은 최신순이며, 요청 목록의 접수순과 표시 방향이 다르다는 점.
- 필터 선택지는 종류별 최대 500개다. 더 많은 링크·작품을 운영할 때의 검색 방식은 후속 검토 대상이다.
- 새 요청은 화면 자동 갱신 없이 새로고침으로 확인한다.
- 링크 관리 권한이 없는 로그인 사용자도 신규 화면 틀에 진입할 수 있지만 API가 차단한다. 화면 권한 안내를 별도로 다듬을 수 있다.
- 자동 승인·대기 순번 보장·결제/환불·이메일 알림은 이번 변경 범위에 포함하지 않는다.

관련 문서: [수신자 액션 설계](recipient-artwork-actions-design.md), [수신자 액션 구현](recipient-artwork-actions.md).

## 8. 거절 후 재요청과 사유 공개 (V60)

- 홀딩 요청이 거절(`REJECTED`)되었거나 판매 취소 요청이 거절(`cancel_rejected`)된 수신자는 같은 버튼으로 바로 다시 요청할 수 없다. 버튼을 누르면 팝업이 현재 상태·사유·처리 시각을 보여주고, 문의 내용을 적어 담당자에게 보낼 수 있다(`INQUIRE`, 한 번에 하나).
- 문의는 요청함의 `재요청 문의` 상태로 모이고 처리 상태가 미확인으로 바뀐다. 관리자는 `재요청 허용`(`ALLOW_RETRY`: 홀딩은 `NONE`으로, 판매 취소는 다시 요청 가능으로) 또는 `문의 거절`(`DECLINE_RETRY`, 사유 필수)로 답한다.
- 수신자 API는 상태와 함께 `notices`(홀딩·판매·문의별 최신 관리자/시스템 사유)를 돌려준다. 시스템 종료 사유는 수신자용 문장으로 바꾸어 보여준다(예: "다른 분께 홀딩이 확정되어 요청이 종료되었어요.").
- 관리자 처리 사유는 액션별 정해진 문구에서 고르고 추가 설명을 덧붙인다. `직접 입력`을 고르면 자유롭게 적는다. 사유는 수신자에게 공개되며 내부 내용은 담당 / 메모에 적는다.
- 아무것도 바꾸지 않는 첫 액션은 빈 요청 행을 남기지 않는다.
- 통합 활동 로그의 작품 이벤트에 작품명·수신자 이메일(요약·행위자 이메일)과 사유를 남긴다.
- 관리자는 확정 홀딩의 기한을 연장한다(`EXTEND`). 홀딩을 해제하지 않으므로 다른 요청이 끼어들 틈이 없다. 새 종료 시각은 현재 종료 시각보다 늦어야 하고, 이미 만료된 홀딩은 연장하지 않는다. 사유는 정해진 문구에서 고르며(선택) 수신자 화면에 "홀딩 기한 연장"으로 표시된다. 수신자는 연장할 수 없다.

### 2026-11-11 검증 결과

- 백엔드 전체 테스트: 426건 중 425건 통과, 1건 건너뜀. 샌드박스의 Mockito JVM 연결 제한으로 실패한 뒤 제한 밖에서 재실행했다.
- 프런트엔드 TypeScript 검사와 두 앱 빌드, 백엔드 JAR 패키징 통과. 입장권 번들 크기 경고는 남아 있다.
- 격리 브라우저 검증: 수신자 인증, 관심·홀딩·구매의사·철회·판매·취소, 통합 이력, 필터, 내부 메모 비공개, 관리자 처리 이력, 모바일 페이지 너비 검사 통과.
- URL 기반 필터 체크박스는 라우팅과 DOM 반영을 모두 기다리도록 검증 스크립트를 보완했다.
- 브라우저 검증은 기존 관리자 경로에서 공통 컴포넌트를 확인했다. 신규 메뉴를 통한 전체 진입 동선과 실제 운영 PostgreSQL 검증은 별도다.
